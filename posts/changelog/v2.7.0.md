# Vix.cpp v2.7.0

Vix.cpp v2.7.0 is out.

This release is an important foundation point for the project. It brings a clearer installation model, a stronger SDK profile workflow, improved release packaging, better platform direction, and more work around CI, tests, diagnostics, registry, and real application validation.

Vix.cpp is still native C++. The source files are C++ files, the compiler is a C++ compiler, and the result is a native executable or library. The role of Vix.cpp is to make the workflow around C++ applications more direct.

## Highlights

- CLI-first installation flow
- SDK profiles installed through `vix upgrade --sdk`
- cleaner separation between the base CLI and optional SDK dependencies
- improved `vix upgrade` workflow
- SDK profile information with modules, dependencies, notes, and install commands
- better release packaging direction
- stronger registry direction
- more focus on CI, tests, diagnostics, and release quality
- Vix Note as part of the developer workflow
- Pico used as real application validation
- post-v2.7 project direction focused on depth instead of more surface area

## CLI-first installation

Starting with v2.7.0, the installer bootstraps the CLI first.

Linux and macOS:

```bash
curl -fsSL https://vixcpp.com/install.sh | bash
```

Windows PowerShell:

```powershell
irm https://vixcpp.com/install.ps1 | iex
```

The first install should be small, predictable, and easy to verify.

After installation:

```bash
vix --version
vix upgrade --check
```

## SDK profiles

SDK profiles are now installed through the CLI.

List available profiles:

```bash
vix upgrade --sdk list
```

Inspect one profile:

```bash
vix upgrade --sdk info web
```

Install one profile:

```bash
vix upgrade --sdk web
```

Install more than one profile:

```bash
vix upgrade --sdk web data desktop
```

Comma-separated profiles are also accepted:

```bash
vix upgrade --sdk web,data,desktop
```

The SDK profile flow is important because different C++ applications do not need the same runtime surface.

A web backend, a data-backed service, a desktop shell, a P2P project, a game-oriented project, and an agent workflow have different requirements. Vix.cpp v2.7.0 makes that separation explicit.

## Common SDK profiles

| Profile   | Use it for                                                                       |
| --------- | -------------------------------------------------------------------------------- |
| `default` | Normal Vix.cpp projects and local development                                    |
| `web`     | HTTP apps, APIs, WebSocket, middleware, validation, crypto, WebRPC, and requests |
| `data`    | Database, ORM, key-value storage, and cache workflows                            |
| `desktop` | Desktop apps using the Vix UI desktop shell                                      |
| `p2p`     | Peer-to-peer networking and local-first systems                                  |
| `game`    | Game-oriented and realtime application workflows                                 |
| `agent`   | Local agent tooling and controlled automation workflows                          |
| `all`     | Full SDK profile for advanced development and release validation                 |

The `all` profile exists for machines that really need the full SDK surface. Most projects should install the profile that matches the application.

## `vix upgrade`

The `vix upgrade` command now has a clearer role.

Upgrade the CLI:

```bash
vix upgrade
```

Install a specific CLI version:

```bash
vix upgrade v2.7.0
```

or:

```bash
vix upgrade --version v2.7.0
```

Check without installing:

```bash
vix upgrade --check
```

Preview changes:

```bash
vix upgrade --dry-run
```

Install a SDK profile:

```bash
vix upgrade --sdk web
```

Install a specific SDK profile version:

```bash
vix upgrade --sdk web --version v2.7.0
```

The command now covers CLI upgrades, SDK profile installation, and global package upgrade workflows.

## Base CLI no longer requires MySQL at startup

Older releases could fail on systems where the MySQL Connector/C++ runtime was not installed.

A common error was:

```txt
vix: error while loading shared libraries: libmysqlcppconn.so.7: cannot open shared object file: No such file or directory
```

In v2.7.0, the base CLI should not require MySQL just to start.

MySQL-related dependencies belong to database/MySQL workflows and SDK profiles, not to the first CLI bootstrap.

This makes the first install more reliable, especially on systems where optional database runtime libraries are not installed by default.

## Vix Note

Vix Note is part of the Vix.cpp developer experience.

It gives C++ developers a visual space for executable notes, examples, experiments, and diagnostics while still using the normal Vix workflow underneath.

Start it with:

```bash
vix note
```

This is useful for working with examples, documenting experiments, and keeping executable development notes close to the project workflow.

## Registry direction

Vix.cpp continues to improve the registry workflow.

The current direction is intentionally practical: keep the registry simple, transparent, and inexpensive to operate while the ecosystem grows.

The registry should make package discovery, dependency installation, updates, local store management, and publishing part of the normal Vix workflow without requiring a heavy cloud backend too early.

Useful commands include:

```bash
vix registry sync
vix search <query>
vix add <package>
vix install
vix update
vix outdated
```

## Performance signal

For v2.7.0, a local HTTP benchmark was run on an HP EliteBook with Linux, x86_64, and 8 CPU threads.

Benchmark command:

```bash
wrk -t8 -c800 -d30s --latency http://127.0.0.1:8080/bench
```

Result:

```txt
3,386,276 requests in 30.09s
112,539.11 requests/sec
```

Latency distribution:

```txt
Avg: 7.31ms
p50: 6.51ms
p75: 7.59ms
p90: 8.73ms
p99: 12.19ms
```

This is not a final universal performance claim. It is a local benchmark on one machine. The important signal is that the HTTP runtime direction is healthy enough to keep testing across more endpoints, concurrency levels, machines, and realistic workloads.

## Real application validation

Vix.cpp is not being validated only through isolated examples.

Pico is a real application built with Vix.cpp. It brings together routing, middleware, persistence, diagnostics, runtime behavior, and the developer workflow around them.

This matters because a runtime can look good in small examples and still fail when different application concerns meet each other.

Pico helps keep the runtime honest.

## Post-v2.7 direction

After v2.7.0, the project direction is not to keep adding more modules or expanding the surface area for its own sake.

The next phase is focused on improving what already exists:

- module quality
- SDK profile workflow
- registry workflow
- diagnostics
- tests
- CI coverage
- release quality
- documentation
- real application validation

New features can still happen, but they should earn their place. A feature belongs in Vix.cpp when it improves the existing workflow, strengthens an existing module, or solves a practical problem for real C++ applications.

The goal is more depth, better maintenance, and stronger confidence in the platform.
